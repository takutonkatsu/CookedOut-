# COOKED OUT! AIアセット・3Dアニメーション制作方針

- 更新日: 2026-09-11
- 状態: 制作方針案
- 対象: コンセプト画像、UI、テクスチャ、3Dモデル、リグ、アニメーション、Unity投入

## 1. 結論

AIは積極的に使える。ただし、用途によって完成度が大きく異なる。

| 対象 | AI適性 | 推奨用途 |
|---|---|---|
| ムードボード・コンセプトアート | 高い | 世界観、色、形、ステージ案の比較 |
| キャラクター三面図の下案 | 高い | 正面・側面・背面の方向性。最終整合は人が修正 |
| 食材・料理アイコン | 高い | ラフ生成後、同じ輪郭・光源・余白へ手作業統一 |
| 背景・広告・ストア画像の下案 | 高い | 構図検討。文字と最終レイアウトは別工程 |
| テクスチャ・デカール | 中〜高 | 権利確認後、シーム・法線・色域を調整 |
| 小物・食材の3Dモデル | 中 | AI生成後にリトポロジー、UV、縮尺、当たり判定を修正 |
| 背景建物の3Dモデル | 中 | 遠景・中景向け。モジュール化とLODを人が整える |
| 主人公の最終3Dモデル | 低〜中 | ベース作成まで。表情、手、衣装、変形品質は人の修正が必要 |
| 自動リギング | 中〜高 | 人型キャラクターに有効。固有体型・動物型は要修正 |
| 移動・待機等の汎用アニメ | 高い | ライブラリやAI補助から開始し、ゲーム用に調整 |
| 調理・受け渡し等の接触アニメ | 中 | 手、器具、相手位置の接触をUnityまたはDCCで修正 |
| 完成品を無修正で製品投入 | 低い | 原則行わない |

## 2. このCodex上でできること

画像生成・編集機能を使って、次を一緒に作れる。

- キャラクター、厨房、料理、車両、UIのコンセプト画像
- 一つの基準画像を参照したバリエーション
- 既存画像の部分修正、色変更、要素追加・削除
- 透明背景のアイコンや切り抜き素材
- スプラッシュ画面、ストア画像、広告クリエイティブのラフ
- 3D化に渡す正面・側面・背面の参照シート

OpenAIの公式画像機能は、テキストからの新規生成、既存画像の編集、複数参照画像、マスク編集、透明背景出力に対応している。[S1]

ただし、公式資料でも、反復キャラクターの完全な一貫性、正確な文字、厳密な構図・配置には制約があるとされている。[S2] したがって、UIレイアウト、ロゴ文字、ピクセル単位のアイコン整列は、生成後にFigma、Illustrator、Affinity Designer等で整える。

この環境の画像生成は2D画像を返す。Unityへ直接投入できるリグ付き3DモデルやFBXアニメーションを、この画像生成機能だけで生成するものではない。3D化には別の3D生成サービスまたはBlender等が必要になる。

## 3. 推奨制作パイプライン

```text
アート方針を文章化
→ 2Dコンセプトと基準シートを生成
→ 採用案を人が修正・確定
→ 3Dベース生成またはBlenderでモデリング
→ リトポロジー・UV・テクスチャ調整
→ 共通骨格へリギング
→ 汎用アニメを生成・流用
→ 調理用アニメと接触位置を修正
→ Unityへインポート
→ iPhone上で見た目・容量・FPSを検証
```

### 3.1 最初にアートバイブルを作る

AI画像を量産する前に、最低限次を固定する。

- 頭身、手足の太さ、顔の比率
- 輪郭の丸さ・角ばり
- 基本カラーパレット
- 材質の種類と光沢
- 光源方向
- 食材アイコンのカメラ角度と余白
- 厨房設備の縮尺
- 禁止表現とOvercookedとの差別化項目

「Overcooked風にして」と指示せず、「丸い大形状、低密度ディテール、遠距離でも読める高い色面分離、柔らかいマット素材」等、必要な造形要件へ分解する。

### 3.2 2Dコンセプト

- 最初は低コストのラフを多数出し、方向性を選ぶ。
- 採用案を正面・側面・背面、表情、配色、持ち物へ展開する。
- 一貫性の基準となる「マスター画像」を一枚決める。
- 新しい画像はマスター画像とカラーパレットを参照して編集・派生する。
- 採用画像をそのまま最終素材にせず、レイヤー分け、輪郭、文字、余白を整える。

### 3.3 3Dモデル

AIのImage-to-3Dは、小物、食材、遠景建物、プロトタイプに向いている。主役キャラクターでは次の修正を前提とする。

- 不要な内部面と重複頂点の削除
- 適切なエッジループへのリトポロジー
- 左右対称と手指・顔の修正
- UVの整理とテクスチャアトラス化
- 実寸スケール、原点、向きの統一
- マテリアル数の削減
- LOD0〜LOD2の作成
- Mesh Colliderを避け、単純Colliderを別作成

Meshy等はText/Image-to-3D、テクスチャ、リギング、アニメーションを提供しているが、プランごとに権利条件が異なる。2026年3月更新の規約では、無料プラン出力と有料プラン出力の扱いが分かれているため、採用時点の規約を資産ごとに保存する。[S3][S4]

### 3.4 リギング

全料理人キャラクターは、可能な限り共通のHumanoid骨格へ統一する。一つのアニメーションを複数キャラクターへリターゲットでき、容量と制作時間を抑えられる。

- 人型二足キャラクター: Mixamo等の自動リグをベースにできる。
- 非人型、極端な短足、四足、触手: 自動リグの成功率が落ちるためBlender等で手動調整する。
- 手の持ち位置、調理器具、顔向きに必要な骨はUnity側で参照できるよう維持する。
- 骨数と1頂点当たりウェイト数は、対象iPhoneの実測に合わせて上限を決める。

Adobeの公式FAQでは、Mixamoは二足人型を対象とし、キャラクターとアニメーションをゲームを含む商用制作物で利用できるとしている。ただし、生データを素材集として再配布しない。[S5]

### 3.5 アニメーション

最初に必要なアニメーションクリップ:

1. 待機
2. 歩く
3. 走る／ダッシュ
4. 物を持つ
5. 物を床・台へ置く
6. 食材を投げる
7. 食材を受け取る
8. 切る
9. 鍋・フライパンを操作する
10. 洗う
11. 消火器を使う
12. 喜ぶ
13. 失敗・焦る
14. 転倒
15. バイク乗車・降車

汎用移動はMixamo等、ポーズと物理感の調整はCascadeur等を候補にできる。CascadeurはAI補助ポーズ、物理補助、モーション生成・修正を提供する。[S6]

調理アニメは、アニメーションだけで手を器具へ完全一致させようとせず、次を組み合わせる。

- キャラクターを作業ソケットへスナップ
- Animatorの共通クリップ
- 手のIKで包丁・鍋・食材位置へ合わせる
- 器具側アニメーションとイベントタイミングを同期
- 実際の当たり判定と工程完了はアニメーションフレームへ依存させない

これにより、体型の違うキャラクターにも同じ調理ロジックを使える。

### 3.6 Unity・iOS最適化

- 原本はBlender／FBX／高解像度PNG等で保存し、Unityインポート設定を別管理する。
- テクスチャは用途別に最大サイズを設定し、iOSではASTCを基本候補にする。
- 食材と小物はテクスチャアトラスと共通マテリアルを使う。
- 背景建物はLODとOcclusion Cullingを検討する。
- キャラクターは共通Avatar、アニメーション圧縮、不要骨削除、`Optimize Game Objects`を実機比較する。
- 透明素材、リアルタイム影、Skinned Mesh数を抑える。
- 画面で小さくしか見えない物へ、生成画像由来の過剰な高解像度を使わない。

Unityはモデルインポートでメッシュ最適化、骨最適化、最大ウェイト数、アニメーション圧縮等を設定できる。[S7]

## 4. アセットの権利・来歴管理

AI生成物も、無条件で安全になるわけではない。最低限、`docs/art/ASSET_PROVENANCE.csv`等で次を記録する。

| 項目 | 内容 |
|---|---|
| Asset ID | ゲーム内で不変の識別子 |
| ファイル | 原本とUnity用ファイル |
| 作成日 | 規約確認日と対応させる |
| 作成者 | 人、AIサービス、外注先 |
| 使用サービス・プラン | 例: サービス名と有料／無料プラン |
| 入力素材 | 所有画像、手描き、文章のみ等 |
| プロンプト | 再現・監査用。秘密情報は入れない |
| 出力ID・URL | 取得できる場合 |
| 利用規約URL・保存版 | 作成日時点の商用利用条件 |
| 帰属表示 | 必要／不要と表示文 |
| 人による修正 | Blender、Photoshop等で行った変更 |
| 公開可否 | 試作限定／製品利用可／要法務確認 |

### 禁止する運用

- 権利のない他ゲーム画像を3D化サービスへアップロードする
- 「Overcookedのキャラクターと同じにする」等、固有表現の再現を狙う
- 有名作家・現役スタジオ名だけを画風指定にする
- 出所不明の無料AIモデルやアニメーションを本番へ入れる
- 無料プランの帰属条件を確認せず、クレジットなしで公開する
- AI出力のロゴ・商標・文字を未確認のままストアへ出す

## 5. COOKED OUT!での推奨分担

### AIへ任せやすい

- 方向性の異なるコンセプト案
- 食材、料理、小物、遠景のラフ
- 表情案、衣装配色案
- UIアイコンの初稿
- テクスチャの初稿
- 汎用人型リグと移動アニメーションのベース

### 人が最終責任を持つ

- アートディレクションと独自性
- プレイヤーキャラクターの最終形状
- 料理アイコンの識別性
- トポロジー、UV、リグ、ウェイト
- 手と器具が接触する調理アニメーション
- iPhone上の負荷、メモリ、容量
- 商標・著作権・利用規約確認

## 6. 最初に作るべきアセット

実装の縦切りでは本番アセットを待たず、グレーボックスを優先する。その後、次の順にAI支援を使う。

1. アートバイブル用の世界観ボード3案
2. オリジナル料理人キャラクター3案
3. 採用キャラクターの三面図と表情表
4. レタス、切ったレタス、サラダ、共通配達容器のアイコン
5. 食材箱、まな板、カウンター、提供口の3D小物試作
6. 共通Humanoid骨格と待機・歩行・切るアニメーション
7. iPhone実機上で視認性と負荷を確認

### 6.1 最初の3D縦切りキット

3Dは9章分を一度に作らず、1-1を実際に遊べる最小キットから始める。

| 群 | 最初に作る物 | 共通化方針 |
|---|---|---|
| キャラクター | 共通料理人体、共通帽子、カピバラ頭部、手、表情3種 | 一つの二足骨格と共通アニメーション。頭部・耳・角・くちばし・尾を種別差替え |
| 容器 | 角形容器、透明蓋、ヒンジ | 開蓋と閉蓋を同一Prefabの状態で管理 |
| 食材・料理 | レタス、切ったレタス、サラダ | 大きな3〜5形状で構成し、細部よりシルエットと色面を優先 |
| 食材箱 | 共通箱、上面カード面、排出口 | 箱本体は一種。カード画像と排出ContentIdを同じデータで差替え |
| 基本設備 | カウンター、まな板、組立・受渡し台、提供口、ゴミ箱 | 一セル寸法、天板高、原点、向きを共通規格化。組立用と受渡し用で別モデルを作らない |
| 動作 | 待機、歩行、持つ、置く、切る、提供 | 共通骨格へリターゲットし、手と器具の接触だけ個別補正 |

この縦切りがUnity上で成立した後、1-2用の鍋・加熱状態、1-3用の低い壁・投擲・バイクを追加する。画像から自動生成したメッシュは、小物のブロックアウトまたは遠景試作に限る。主役キャラクターと一セル設備は、Blender等でクリーンなトポロジー、UV、マテリアル数、ピボット、LOD、単純Colliderを整えてからFBXまたはglTFでUnityへ渡す。

#### Unity受け渡し規格の初期値

- 1 Unity unit = 1 m。グリッド一セルの実寸はグリッド仕様側で一つに固定する
- +Yを上、+Zを正面とし、床設置物の原点はセル中央の床面
- 設備は一セル境界内へ収め、操作点とColliderをメッシュから分離する
- 可動蓋、鍋、フライパン、橋、回転島、リフトは可動部ごとに別Transformを持つ
- マテリアルは共通アトラスを優先し、クリーム、濃灰、琥珀、ティールを共有する
- 画像内座標や画像から推測した寸法を使わず、正本のグリッドデータとInteraction契約を使う
- AI生成または外部素材は、利用条件、入力、修正内容、出力ファイルを`ASSET_PROVENANCE.csv`へ記録する
