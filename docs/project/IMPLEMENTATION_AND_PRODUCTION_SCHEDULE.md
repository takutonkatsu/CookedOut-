# COOKED OUT! 完成までの実装・制作スケジュール案 v0.2

- 更新日: 2026-09-11
- 状態: 直近方針を決定。公開規模と作業時間を確認後に暦日を固定する
- 対象: 機能、3D、アニメーション、UI、出張営業、配達街、オンライン、サーバー、音、QA

## 1. 結論

直近は、出張営業第1章1-1〜1-8と本店通常営業の基本一周を、小さな製品版として完成させる。オンライン協力、セーブ、分析、実機QAもこの範囲へ含める。同時に全54出張ステージを企画カードまで設計し、厳密なグリッド配置は第2章から章単位で順次確定する。詳細なGateと完了条件は[第1章＋通常営業 Core Alpha計画](CHAPTER1_AND_NORMAL_BUSINESS_CORE_ALPHA_PLAN.md)を正とする。

期限は、ソロ第1章と通常営業の一周を中心とする`Core Alpha Feature Complete`を2026-09-25までとする。全8面の2〜4人オンライン、クラウド、製品美術、十分な実機バランスまで含む安定化版とは分ける。詳細は[Core Alpha 2週間スプリント案](CORE_ALPHA_TWO_WEEK_SPRINT.md)を参照する。

以下の三本のゴールデン縦切りは独立した最終目標ではなく、Core Alpha内の中間Gateとして維持する。

本作の主な遅延要因は、基礎コードではなく、次の三つになる可能性が高い。

1. 固定俯瞰・iPhone実機で見た時のキャラクター、料理、設備、UIの美術修正
2. 54出張ステージの個別レイアウト、周期、人数別バランス
3. 街での配達操作、道路構造、厨房との往復時間の調整

したがって、全機能を先に完成させてから全アセットを作る順序にはしない。次の三本を「完成見本」として早期に作り、その中で機能、見た目、操作、音、実機性能の基準を固定する。

| 完成見本 | 検証する柱 | 完成条件 |
|---|---|---|
| 1-1 ゴールデン厨房 | 基本料理、キャラクター、設備、容器、厨房HUD | iPhoneで一注文が製品に近い見た目と操作感で完了する |
| 1-3 ゴールデン配達 | 投擲、バイク、街、配達HUD、厨房復帰 | 短い街区で厨房と配達の両方が楽しい |
| 1-8 ゴールデン協力 | 動的厨房、自前／代行、2〜4人協力 | 代表的な変形厨房をオンラインで完走できる |

この三本を通過するまで、36料理、12キャラクター、54ステージの本番3Dを一括量産しない。

## 3. 推奨する順番

### フェーズA — 実機基準と制作安全性

目安: 1〜2週間

- 現在の1-1、1-3、1-5を実機へ入れ、親指操作、画面密度、30fps、発熱を確認する
- カピバラ、P0厨房、料理状態、HUDを実際の固定カメラで承認する
- Gitの基準コミット、非公開リモートまたは別媒体バックアップ、TestFlight用設定を用意する
- 修正依頼は「その画像だけの修正」で終わらせず、ビジュアル基準、生成スクリプト、Prefab検査のいずれかへ一般ルールとして残す

停止条件: 実機で基本操作と基準アセットが承認されるまで、残る11動物と36料理の本番量産を始めない。

### フェーズB — 三本のゴールデン縦切り

目安: 4〜7週間

1. 1-1を製品品質へ近づける
2. 1-3の小さな街区、バイク、ミニマップ、厨房復帰を仕上げる
3. 1-8用の接続島、自前／代行を単独プレイで完成させる
4. 共通キャラクター骨格と基本アニメーションを固定する

最初に作る共通アニメーションは、待機、歩行、ダッシュ、取る／置く、運搬、作業、投擲、失敗／慌てる、乗車の9群に限定する。全動物は同じ骨格とクリップを使い、頭部、耳、角、くちばし、尻尾だけを種別補正する。動物別の専用モーションは初期版の完成条件にしない。

### フェーズC — オンライン協力の技術リスクを先に潰す

- 最初は1-1の2人同期だけを作る
- 移動、所持品、設備操作、注文、投擲、切断・復帰をサーバー権威境界へ接続する
- 次に1-3の厨房／配達分離、最後に1-8の動的厨房を同期する

各ステージは必ず次の順にする。


ユーザーが白紙から54ステージの座標を考える必要はない。ユーザーが決めるのは「どんなハチャメチャさか」「どんな受け渡しをさせたいか」「配達あり／なし」「採用候補」の四点とし、具体的なグリッド候補、設備座標、周期初期値は仕様側と実装側で複数提案する。

## 5. デザイン修正を減らす運用

### 5.1 ラスター画像ではなくゲーム画面で承認する

画像生成結果だけを承認しても、固定俯瞰、HUD、照明、LOD、アニメーションが重なると印象が変わる。以後の最終承認はUnityの実カメラとiPhone実機で行う。

### 5.2 一体から段階量産する

- キャラクター: カピバラ1体 → 追加3体 → 残り8体
- 料理: サラダ・スープ・フライパン料理の3基準 → 9系統 → 36系統
- 厨房: 1-1 → 1-3 → 1-8 → 章キット → 個別ステージ
- アニメーション: 共通9群 → 4体同時検証 → 種固有補正

各段階で承認するまで次の大量バッチへ進まない。

### 5.3 修正を再利用可能な規則へ変える

例:

- 「にんじんが芋に見える」→ 食材シルエット比の制作規則と自動検査
- 「顔が目立たない」→ 頭身、手持ち位置、カメラ占有率の共通基準
- 「設備用途が分からない」→ 大きな立体ピクトと設備固有輪郭の共通規則

同じ指摘を別アセットで繰り返さないことを、制作効率の指標にする。

### 5.4 同時作業数を制限する

- 美術の未承認マスターは同時に一種類まで
- グレーボックス中の新規ステージは同時に最大3件
- 一章のレイアウトが固まるまで次章の本番背景を量産しない
- 機能担当は美術待ちの間、テスト、データ基盤、オンライン、ツールを進める

## 6. 配達する街の作り方

54ステージごとに別の街を作らない。初期版では次を共通化する。

- 本店周辺の小型街区一つを通常営業の中心にする
- 道路は短距離、中距離、長距離の三ルート帯を組み替える
- 配達先は建物外観ではなく、道路グラフ上の有効ノードから選ぶ
- 交通、工事、群衆、天候は同じ街へ重ねるイベントレイヤーにする
- 出張営業の外部配達は、そのステージ専用の短い配達路だけを追加する

最初に1-3で「交差点一つ、分岐一つ、配達先二つ、帰還路一つ」を完成させる。面白さが確認できてから街区を広げる。

## 7. ユーザーの判断が必要な場面

ユーザーの時間を、座標入力や量産チェックではなく次へ集中させる。

1. iPhone実機での見た目と操作感の合否
2. カピバラ、厨房、料理3基準、共通アニメーションの最終方向
3. 各出張ステージの狙いと、提示されたレイアウト候補の選択
4. 街の広さ、配達時間、運転の気持ちよさ
5. ソフトローンチで出すステージ数と収益化頻度

コード構造、定型データ化、自動検査、候補レイアウト生成、端末テスト表、アセット台帳更新は実装・仕様側で進める。
