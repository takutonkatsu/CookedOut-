# COOKED OUT! 定番・おすすめ献立と店の体験をつなぐ設計案 v0.1

- 作成日: 2026-09-13
- 採用方針: 機能・世界内の意味・操作・結果を一つの流れにする。ユーザー承認済みの所持／未配置判定と配置維持を反映する
- 未決定: 献立方式、固定部分の決め手、名称、更新周期、固定／選択部分の配分、引き直し、再営業の再生成
- 保留維持: 料理の具体材料・工程・個別レシピ。今回これらを再提案しない
- 性格: 比較・相談資料。実装や画像生成は行わない
- 後続決定（2026-09-13）: 系統と個別レシピを分けた献立を採用。通常営業は序盤1系統、途中から定番1系統＋おすすめ1系統を標準とする。未解放派生は出さず、個別レシピ単位で注文・点数・設備判定を扱う。本書中の旧未採用表現より本項を優先する。ただし定番の指定・更新規則と移行Lv、候補更新・注文比率は未確定

## 1. ユーザーの意図

単に選べる機能を作るのではなく、「店主として献立を考える」「出張で覚えた料理を本店で出す」等、ゲーム内の行動として意味がつながる設計にする。

出張で技術・レシピを習得する、本店で献立へ取り入れる、必要な厨房を整える、営業して売上・評判を得る、設備を育てて次の挑戦へ進む。この因果関係を、実際の解放・選択・結果表示へ反映する。

「店らしい名前を画面へ付ければよい」で終わらせない。一方で細かな経営シミュレーションや会話を増やす要望とは解釈しない。

## 2. 献立方式の比較

| 方式 | 利点 | 注意点 |
|---|---|---|
| 定番＋営業ごとの選択枠 | 店の継続性と、今回どう営業するかという店主の判断を両立する | 追加で料理数・必要器具を増やしすぎない。固定部分を誰が決めるかが必要 |
| 規則で全献立が決まる | 準備が短く、解放・難度・収入を調整しやすい | 本店なのに毎回提供料理を指定される理由が必要。通常営業が課題ステージの連続に寄りやすい |
| 献立全体を毎回3候補から選ぶ（前案） | 少ない操作で幅のある選択ができる | 全体が毎回入れ替わると店の定番が感じにくく、候補引き直しが準備の主作業になる可能性 |

現テーマでは「定番＋営業ごとの選択枠」を第一推奨にする。ただし採用は未決定。

## 3. 第一推奨案

### 3.1 名前

- 変えずに出す部分: 「定番メニュー」を推奨。「看板メニュー」は特に代表的な一品の意味が強く、必ずしも固定部分全体の呼称には向かない。
- 今回選ぶ部分: 「本日のおすすめ」を推奨。「日替わりメニュー」も候補だが、現実の日付更新を期待させないよう更新単位を定める必要がある。
- 全体の画面名: 「本日のメニュー」または「営業準備」。名称はどれも今回確定しない。

「定番」は毎回システムが別の料理へ入れ替えるものではなく、普段は維持する意味にする。最初に推奨の定番を用意し、プレイヤーが営業外のメニュー編集で見直せる案。これもユーザーの「固定」が開発側完全指定を意味する場合とは異なる追加提案なので、確定しない。

定番を変更できても、毎営業の必須選択にはしない。未解放料理や必要設備を満たさない料理は候補にせず、選んだ営業Lvで成立する献立構成に制限する。

### 3.2 営業前の行動

1. 維持されている定番メニューを確認する。
2. 解放済み料理と所持設備から作る3候補の中で、本日のおすすめを選ぶ案。
3. 定番とおすすめを合計した必要設備・供給口数・厨房容量を確認する。
4. 今の配置が有効ならそのまま開店。必要な時だけ配置変更する。
5. お客の注文は、決めた献立の範囲から自動で入る。プレイヤーが注文を発行するのではない。

おすすめは追加の報酬モードや別営業ではなく、同じ営業内の献立枠とする。定番とおすすめで別スコア・別通貨を作らず、料理基本点・チップ・納品コインの共通ルールを使う。

一営業の料理系統数・注文派生数・食材供給数の上限は両者の合計へ適用する。初期に単一料理系統しか扱わない営業では、その系統内の派生の入替等で選択を成立させ、別の料理系統を無理に追加しない。具体派生は料理検討再開まで決めない。

定番とおすすめをどの比率で注文へ出すか、変更せず前回おすすめを維持できるか、3候補を更新できるかは未決定。39の無制限引き直し案を自動継承しない。

### 3.3 日付との関係

現行は睡眠・現実の一日・来店時間帯で営業を強制しない。おすすめ選択のためだけに現実の翌日まで待たせる方式は推奨しない。

営業を一つの区切りとし、「今回の営業で出すおすすめ」として準備時に選べる案。表示に「営業ごとに変更できます」を添える等で理解を助ける。日替わりを正式名称にしたい場合でも、現実の24時間制とゲーム内の営業単位を混同しない。

## 4. 全献立を規則固定にする場合

ルール固定自体は不適切ではない。初回導入や出張には、習得テーマ・会場からの依頼という理由を付けやすく、操作の学習へ集中できる。

通常営業全体で採用するなら「誰が、なぜ提供料理を決めるのか」を説明できる必要がある。出張の依頼とは別に本店にも毎回の指定依頼を設けると、自分の店を営む役割が弱くなる可能性がある。

店ランク、解放状況、所持設備から安全な献立を自動提案し、変更したい人だけ触れる方式なら、準備の短さと店主の選択を両立できる。ただし今回はこちらを採用済みにはしない。

## 5. 名称だけでごまかさないための確認例

| 機能 | 店の体験としての意味 | 挙動で守ること |
|---|---|---|
| 料理解放 | 出張で覚えた料理を本店で出せる | 習得前の料理を候補に混ぜない |
| 献立選択 | 開店前に何を提供するか決める | 選んでいない料理の注文を営業中に追加しない |
| 設備確認 | 選んだ献立を作る準備 | 所有済み未配置なら配置で解決し、買い直しを求めない |
| 配達代行 | 厨房の仕事を続けるため配送を任せる | 目的地までの時間・受付上限が操作前に分かる |
| 店の成長 | 営業実績と習得・設備が次の挑戦につながる | 昇格条件と未達理由が確認できる |

スコアやランキングまで全て現実の売上へ置き換える必要はない。スコアとコインを分けた既定仕様を、世界観の名目で再び比例させない。必要なゲーム上の抽象表現は明快に残す。

## 7. 定番の自動決定とスコアによる献立移行の比較

ユーザーから、定番をゲーム側で規則的に決める案と、自由選択だが高効率な料理へ移行しないと評判を得られない案が提示された。どちらも検討段階であり、今回は定番の決定権・新たな評判条件を確定しない。§3のプレイヤーによる定番編集も未採用案として残す。

### 7.1 スコアによる誘導が成立する条件

現仕様では現在最高営業Lvの星1以上で評判を得る。星1／2／3は80／140／220評判で、通常営業の星基準は営業Lv別に固定し、献立ごとには変えない。したがって、上位営業Lvの星基準に対して処理効率の低い献立が星1へ届かない場合、既存の仕組みだけでも献立を見直す動機になる。

ただし料理基本点の高さと時間当たりの得点は同じではない。説明用にチップを除けば、基本点40を20件納品すると800点、基本点100を6件なら600点。これは4分の実測予測ではなく、高い一皿点だけでは効率を保証しない例である。

実際には準備時間、器具占有、並列化、移動、配送先・まとめ配送、チップ、失注を含めて比較する必要がある。料理詳細を保留している現段階では、数値だけで自然な献立移行が起こると保証できない。

### 7.2 自由選択を星1不達で強制するリスク

- 開始可能と提示された献立が、推奨設備で適切に遊んでも星1へ到達不能だと、料理選択の隠れた正解を探すゲームになる。
- 高効率料理だけを選ぶ正解が一つに収束すると、店主の選択も厨房の多様性も薄れる。
- 同じ献立・配置のまま設備を強化して再挑戦する既定の成長ループが、料理変更だけで解決／料理変更以外では解決不能になると、設備育成の意味が弱まる。
- 新料理を広めたい理由で点数を過剰に上げると、コインも納品基本点連動なので経済へ同時に影響する。

すべての過去料理を最高営業Lvで永久に同格にする必要はない。ただし、そのLv向けに有効な候補として提示する献立には複数の星1到達経路を用意し、星2・3で選択・設備・配置の効率差を出す案を推奨する。低Lvでの旧献立反復は引き続きコイン稼ぎとして残す。

### 7.3 今回の第一推奨

カジュアルさと準備負担を考慮すると、定番はゲーム側が進行に沿った規則で指定し、おすすめ部分はプレイヤーが選ぶ組合せを第一推奨とする。これにより§3の「定番も最初に自分で選び直せる」案より、毎回の判断を一つ減らせる。まだ採用決定ではない。

- 定番は毎営業のランダム抽選にはしない。選択中の営業Lvと料理解放段階から決まり、同じ営業Lvでは基本的に維持する案。
- 店ランク上昇で新しい営業Lvへ挑む時、節目で定番の一部を新しい品ぞろえへ更新する。毎ランク全品交換は要求せず、未解放料理・未所有必須設備を要求しない。
- 低い営業Lvへ戻った場合はそのLvの定番を使い、現在店ランクが高いだけで過去の献立を差し替えない。営業途中も変更しない。
- 成長の意味付けは「店の成長に合わせて品ぞろえを広げる」。自動指定される料理を、プレイヤーが自ら開発・選定したと偽って説明しない。客の好み・人気度・仕入れシミュレーションを新設する必要はない。
- 自由に選ぶおすすめ部分では、同じLvで複数の成立する選択肢を用意する。効率の良い組合せで星2・3と評判獲得速度を伸ばす。
- 店ランク昇格の既定条件や星1／2／3評判値は変更しない。特定料理の必須提供回数や専用昇格課題を追加する案ではない。

### 7.4 自由選択を優先する場合の代案

定番まで自由選択にするなら、先に営業Lvの目標スコア・推奨工程を明示し、標準的なおすすめ構成を用意する。「自分で選べるが、失敗するまで不適合が分からない」を避ける。複数の有効献立、設備強化、動線改善、自前／代行の選択から目標へ近づけるようにする。

この方式はプレイヤー主導性が強い一方、全解放料理からの組合せ検証・初心者案内・収入均衡により多くの設計と検証が必要になる。今回どちらを採用するかは保留とし、基本点や猶予だけを先に調整して解決した扱いにはしない。

## 8. 2品ではなく2料理系統と複数派生で献立を作る

ユーザーから「パスタ＋サラダ」の2系統を選び、パスタ内にトマト・ツナ・トマトツナ、サラダ内にレタスのみ・レタスとトマト等の派生を持つ案が提示された。既存07の料理系統と注文派生の構造に合致する。通常営業の標準を2系統にする案として推奨するが、全営業・出張へ2系統を強制する決定ではない。

### 8.1 管理する単位

| 単位 | 例 | 用途 |
|---|---|---|
| 料理系統 | パスタ、サラダ | 定番・おすすめの選択、分類・紹介 |
| 個別レシピ（注文派生） | トマトパスタ、ツナパスタ等 | 材料・工程・基本点・完成判定・注文画像・解放状態 |
| 工程文法 | 切って組立、鍋と別部品の合流等 | 複数系統で共用する調理の仕組み |
| 営業の献立 | 今回有効な系統と個別レシピの集合 | 注文生成の範囲、合算した必要設備・供給口確認 |

系統名だけで材料・点数・設備を一律に決めない。同じ系統の派生でも必要工程が違うことがあるため、今回有効な個別レシピから必要設備を集計する。

### 8.2 ユーザー例での読み方

- パスタ系統: トマトパスタ、ツナパスタ、トマトツナパスタの3レシピ。
- サラダ系統: レタスサラダ、レタス＋トマトのサラダの2レシピ。
- 合計2系統・5種類の注文候補になる。2品だけを交互に繰り返す意味ではない。
- 5種類の注文候補を持っていても、同時に5注文を表示する義務はない。同時注文上限は別の難度設定。
- 「パスタ＋サラダ」は営業中に提供する2系統を意味し、一注文で二品をセット納品する意味にはしない第一案。各注文票は個別レシピ一つを指定する。セット料理の追加とは別に扱う。

この例は分類と選択単位の説明として扱う。具体食材数、ツナ等の加工状態、調理器具・秒数・点数をここで確定せず、材料・工程検討の保留を解除しない。

### 8.3 定番とおすすめへ適用する案

定番をゲーム側が指定する方式を採用するなら、定番1系統＋本日のおすすめ1系統を標準形にする案。例えば定番がパスタ、その営業に組み合わせるおすすめとしてサラダ系統を選ぶ。

系統内の個別レシピまでプレイヤーが毎営業一つずつ選ぶ操作は、初期の推奨案には加えない。解放済み・営業Lvに合う派生をゲーム側が候補化し、営業前にどの料理が出るか一覧で示す。個別レシピの選別をやり込みとして追加するかは将来の別判断。

定番とおすすめの双方から通常の注文票が流れ、片方に専用注文UIや別スコアを作らない。系統と派生の出現比率は別に持たせ、派生が3対2だから機械的にパスタ注文が60%になるとは決めない。具体比率は未確定。

合計の料理系統数だけでなく、派生数、食材供給数、必要器具、同時にできる手作業も確認する。単独で可能な2系統でも、組み合わせると供給口や設置容量を超える場合はおすすめ候補から外す。

### 8.4 2系統でも難度・多様性を作る

- 加熱待ちの間にもう一方の下処理をする。
- 共通食材をどちらの注文へ回すか判断する。
- 同じ基本料理を注文派生に合わせて仕上げる。
- まな板・鍋・組立面が競合する順序を調整する。
- まとめ配達と代行枠を使い分ける。

終盤を難しくするためだけに3系統・4系統と増やす必要はない。2系統のまま派生・工程の重なり・配送判断・注文負荷を変える案を優先する。ただし、注文が存在しても全工程が同時待ちになっていれば忙しさは生まれないため、具体レシピ再開後に検証する。

新料理導入や序盤の一系統営業は残す。出張は各面の主題に合わせた既定の1〜3系統設計を維持し、本案だけを理由に全ステージを2系統へ変更しない。

### 8.5 決定していない事項

定番を誰が決めるかという前節の二案、通常営業2系統の適用開始Lv、系統内派生の解放単位・数、注文出現割合は未決定。現在の大枠は「系統と個別レシピを分けて管理する」という既存構造の明確化であり、全36系統の名称・分類見直しや第1章具体レシピの承認ではない。
