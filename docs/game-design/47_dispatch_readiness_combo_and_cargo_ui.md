# COOKED OUT! 出荷準備順コンボと積載取出しの改訂案 v0.1

- 作成日: 2026-09-13
- 後続整理: コンボの対象列・倍率推移・失敗後の再開値・事故再積載を含む具体例は49を参照。49は確定前の詳細案であり、ユーザーの詳細説明依頼だけで全ルールを採用済みとしない
- 採用: 空手で荷台へ置く／取るを押した時に積荷アイコン一覧を開く。時間帯を乗車／代行受付時に保持し、得点は到着時に加算する分離
- 変更方向: 実到着順のチップ評価をやめ、厨房での出荷準備順を評価する。配達は自由な巡回順の最適化を楽しむ
- 提案・未確定: 初回積載時の順序判定、取り出し後の注文対応維持、一覧でタップ即取出し、地図強調の変更。コード・実機値は変更しない

## 1. 積荷を取り出す操作

料理を持って置くなら空き枠へ追加、空手で置く／取るなら一覧を開く。近づいただけでは一覧を出さず、一覧を開いた時点でも料理を取り出さない。

一覧で料理アイコンをタップすると、その1個を手に取り一覧を閉じる案。閉じる操作だけなら何も取り出さない。積荷が一つでも同じ手順を第一案として一貫させる。近隣の共有荷台で他プレイヤーが先に取った場合は選択時に在庫を再確認し、複製を発生させない。オンラインだから営業時間を一時停止するUIにはしない。

## 2. 判定時点の比較

| 候補 | 特徴 | 問題 |
|---|---|---|
| 初回積載時（推奨） | 荷台へ置く／代行棚へ置くという対応した動作で評価できる。積載後に厨房の次注文を代行へ出せる | 積み直し・取出し・ルート切替で二重判定しない設計が必要 |
| 乗車時 | 発送確定とまとめられる | 古い注文を積載済みでも、新しい注文を代行へ出す前に乗車を待つ。まとめ積載と競合する |
| バイクが実際に動き始めた時 | 見た目の出発に近い | ブレーキ保持、接触で移動、微小な入力等で判定が曖昧。乗車時案より利点が小さい |

推奨は料理が正しい注文の出荷準備へ初めて受理された瞬間。実際の調理完成時刻そのものではなく、完成料理を荷台／代行棚へ置く行為を基準とする。現地提供は提供口での受理時とする既存構造を維持する。

## 3. 一つの共通コンボで運用する案

まだ出荷準備判定をしていない注文のうち最古が次の対象。自配達の初回積載と代行の受付を同じ列で一回だけ判定し、その注文に倍率を記録する。出荷準備済みなら、未出発でも次の順番判定から除く。実際に配送しない限り得点は得ない。

例: 1を荷台へ積む→2を代行へ預ける→3を荷台へ積む。これで1・2・3の順番評価がつながる。その後にバイクで3→1の順に届けても倍率は変わらず、2の実到着時刻にも依存しない。

| 項目 | 自配達 | 代行 |
|---|---|---|
| 注文順倍率を記録 | 正しい注文への初回積載 | 受付 |
| 注文タイマー停止・時間帯保持 | 乗車 | 受付 |
| 通常チップ額を計算可能にする | 乗車（保持時間帯×記録済み倍率） | 受付 |
| 得点・納品基本点によるコインを加算 | 実到着 | 実到着 |

注文ごとの記録済み倍率は、その後ほかの注文でコンボが切れても遡って変更しない。積載だけでは未発送上限を空けたり、新注文の成功補充を発生させたりしない案。注文供給の具体方式・上限は36の検証待ちのまま。

## 4. 積み直し・入替の悪用を防ぐ最小ルール案

- 判定は料理を置く回数ではなく注文ごとに一度だけ。積み直しても倍率は増えず、順番外の記録を後から順番内に直せない。
- 一度受理した料理には注文番号を紐付け、取り出して台へ戻しても同じ注文向けの料理として表示する。別の同一レシピ注文へ次々と読み替えて、一皿で複数注文のコンボを進めることはできない。
- 乗車前は取り出し・別バイクへ積み直し・代行への切替を可能とする案。注文番号と判定済み倍率を維持し、切替だけで再判定しない。配送方式は最終発送時に決まり、未発送ならタイマーは進み続ける。
- 荷台内・取出後に未発送のまま失注した時は、既定の失注減点と共有コンボリセットを行う。過去に別注文へ記録した倍率は遡って取り消さない。
- 失注時も料理を自動消去せず、失効した注文との紐付けを解除して将来の同一レシピ注文へ利用できる既定方針を維持する。失注ペナルティがあるので無償の順序判定やり直しではない。
- 誤レシピや対応する未完了注文がない料理ではコンボを進めない。未対応料理を物理的に積めるか、受理を拒むかは別途決める。
- 料理を捨てた場合の作り直し・注文対応の復旧、二人が同じレシピを同時積載する場合の割当とイベント整列は検証する。番号対応はUIで見せ、隠れた予約扱いにしない。

取出しでコンボ履歴を巻き戻す方式は、その間に仲間が処理した注文へ影響するため推奨しない。取出しを全面禁止する方式も、承認済みの入替操作と矛盾するため採らない。

## 5. 配達と厨房で優先表示を分ける案

厨房の注文票では次の出荷準備対象を強調し、積載済みは準備済み表示と残りタイマーを示す。配送中は乗車後の状態であり、準備済みと区別する。

街の地図には全行先を示し、自分の積荷の届け先と選択中のナビ対象を強調する。古い注文を配達するほど倍率が上がる表示は使わない。初期ナビ先を近い未完了行先にするか、前回の選択を維持するかは今後検討。自動で巡回順を決めて拘束せず、選択変更可能とする。

順序自由化により自配達の移動効率と得点/分が変わるため、既存の代行比5〜10%高い調整目標と係数を実測し直す。自由順だけで必ず面白くなるとは断定せず、近接行先の組合せ・道路分岐・厨房の加熱時間と合わせて試す。

## 6. 未決・検証

- 初回積載か乗車かの最終承認。
- 多人数時の一皿一注文対応、同時受付、取出後の再発送で重複加点しないこと。
- 準備済みでも出発を待つ間にタイマーが進むことが伝わるか。
- 同一食材一皿の複数注文への使い回し、未納品注文での倍率仕込みが過度に有利にならないか。閉店未納品は無得点、発注上限を積載だけで解放しない条件で検証する。
- 共通コンボのために乗車を待つ問題が減り、同時準備とまとめ配達が両立するか。

## 7. 積み直しの説明とヒント方針

ユーザーから「積み直ししたらコンボは確定で途切れるということか」と確認があった。前案の意味は、積み直し自体では共有コンボを切らず、最初の判定を保存して再判定しないというもの。積み直しで強制リセットする仕様を新たに採用したとは扱わない。初回積載時判定などの未確定事項を、この確認だけで一括確定しない。

- 順番どおりに初回積載→取出し→再積載: 取出し・再積載それ自体ではコンボに影響しない。
- 順番外に初回積載→取出し→再積載: 最初の順番外判定で切れた履歴は消せない。積み直しで復活しない。
- 取出し中に別注文の順番外処理や失注が起きた場合: その別イベントで共有コンボが切れることはある。積み直しが原因ではない。

ヒント・遊び方へ分かりやすく載せる方針をユーザー依頼として採用する。仕様確定後の表示文候補:

> 注文順の判定は、最初に積んだときの1回だけ。積み直してもコンボは増減しません。

遊び方の詳細には、順番外の初回判定を積み直してもやり直せないこと、乗車前は注文タイマーが進むことを分けて示す。初めて積荷を取り出す時の短い非遮断ヒントも候補とし、毎回の確認ダイアログは追加しない。文面は判定方式の確定に合わせて更新する。
