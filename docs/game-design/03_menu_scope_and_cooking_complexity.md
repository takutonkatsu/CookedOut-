# 店の業態と料理工程の多様性 — 検討メモ v0.1

> **履歴資料:** 本書には旧試作案が含まれます。ピザは廃止、加熱器具は鍋とフライパンに限定する現在方針については[最新基本ゲーム仕様](CURRENT_GAME_SPEC.md)を参照してください。

## 現在の結論

Cooked Out!をピザ専門店として設定しないことを決定した。

店の業態を、次の形に決定した。

> 街の小さな店から始まり、店頭営業、近隣配達、イベントへの出張営業を行う「ケータリング食堂」。

ピザは店の正体ではなく、最初に覚える料理として残す。ゲームが進むと、焼く、煮る、焼き付ける、冷たいまま組み立てる、という異なる工程系統を少しずつ追加する。

これにより、次を両立できる。

- ピザの分かりやすさと配達との相性をMVPで利用できる
- ゲーム全体を一つの調理工程へ固定しない
- 出張営業ごとに依頼主や会場に合ったメニューを出せる
- 多国籍料理を無制限に増やす必要がない
- 厨房設備の追加が本店成長として目に見える

## 1. ピザ専門店の長所と限界

### 長所

- 生地、ソース、具材、焼成、カット、箱詰めが見た目で理解しやすい
- 箱に入れてバイクで運ぶ理由が自然
- 具材違いを同じ設備で増やせる
- 一枚の大きな完成品なので、受け渡しの状況が読みやすい
- オーブンが明確なボトルネックになる

### 限界

- 多くのレシピが「具材を変えて同じ順番を繰り返す」形になる
- 鍋料理のようなバッチ管理や、別々に加熱した部品の合流が生まれない
- 設備成長がオーブンの台数と速度へ偏りやすい
- 長期的には、厨房より出張営業ギミックだけが変化を担当することになる

ピザは良い導入料理だが、ゲーム全体を支える唯一の料理系統としては幅が狭い。

## 2. 業態の選択肢

| 案 | 強み | 弱み | 評価 |
|---|---|---|---|
| ピザ専門店 | 覚えやすい、配送しやすい、テーマが明快 | 工程と設備の変化が少ない | 作品設定としては不採用 |
| 何でも作る多国籍レストラン | レシピを自由に増やせる | 店の個性が弱く、コンテンツ範囲が膨らむ | 非推奨 |
| 洋食店・ダイナー | ピザ、バーガー、スープをまとめやすい | 出張営業との接続がやや弱い | 有力 |
| デリバリー専門キッチン | 配達との整合性が高い | 店頭営業や店の愛着が弱くなりやすい | 部分採用 |
| ケータリング食堂 | 店頭、配達、出張営業、多様な依頼食を一つにできる | 名前と世界観の見せ方が必要 | **採用** |

「ケータリング食堂」はゲーム内で必ずこの固い名称を表示するという意味ではない。世界観上は「町の料理店」「みんなのキッチン」など親しみやすく呼び、システム上の業態としてケータリング機能を持たせる。

## 3. 器具の数ではなく、工程グラフを変える

料理の多様性は、調理器具を大量に並べることではなく、作業がどこで分岐し、どこで合流するかで作る。

### 系統A — 組み立ててから加熱

代表: ピザ、グラタン

```text
生地・器
＋ ソース
＋ 具材
→ 組み立て
→ オーブン
→ カット／箱詰め
```

特徴:

- 注文ごとの差を早い段階で決める
- オーブン前に仕掛品が溜まる
- 焼く順番とオーブン管理が中心になる

### 系統B — 部品を別々に作って最後に合流

代表: バーガー、ホットサンド

```text
肉 → 鉄板 ─────┐
野菜 → カット ──┼→ 組み立て → 包装
パン ─────────┘
```

特徴:

- 二人以上で自然に分業しやすい
- 一部だけ完成して置き場を圧迫する
- 足りない部品を声に出す機会が多い

### 系統C — 一つの設備で複数食分を作る

代表: スープ、カレー、パスタソース

```text
複数食材をカット
→ 鍋へ投入
→ 煮込み
→ 2〜3食へ取り分け
→ 容器詰め
```

特徴:

- 一つの鍋をどの注文へ使うか考える
- まとめ調理と注文期限のトレードオフが生まれる
- 鍋を空にして次を仕込む判断が発生する

### 系統D — 加熱せず、注文ごとに組み合わせる

代表: サラダ、サンドイッチ、デリ盛り合わせ

```text
食材Aをカット
＋ 食材Bをカット
＋ 注文別トッピング
→ 盛り付け／包装
```

特徴:

- 焦げない代わりに作業台と食材管理が忙しい
- 動的厨房や配達が難しい回の認知負荷調整に使える
- 新しい出張営業ギミックの導入料理に向く

## 4. 初期設備の上限案

完成版の初期章では、機能設備を次の6種類までに抑える。

1. 食材箱
2. 下処理台
3. 組立・盛付台
4. オーブン
5. 鉄板
6. 鍋・コンロ

箱詰め台、配達棚、洗い場は料理固有設備ではなく、営業共通設備として扱う。

初期段階では、フライヤー、蒸し器、ミキサー、ブレンダー、麺ゆで器などを追加しない。同じ入力を使う器具でも、画面上で監視すべきタイマーが増えるためである。

## 5. 複雑さの上限

### 一つの料理

- 必須工程: 3〜5工程
- 同時に加熱する部品: 最大2種類
- 注文別の選択具材: 最大2個
- 専用器具: 最大1種類
- 完成直前の合流: 最大3部品

### 一つの営業

- レシピ系統: 最大2系統
- 表示する個別レシピ: 2〜4種類
- 使用する加熱器具: 最大2種類
- 初登場要素: 新レシピ、新器具、出張営業ギミックのうち一つだけ
- 激しい出張営業では、既知の料理1系統だけを使う

「工程数が多いほど難しい」にはしない。難易度は、同時注文、設備共有、受け渡し距離、加熱タイマー、配達順の組み合わせで作る。

## 6. 推奨する導入順

| 段階 | 料理系統 | 設備 | 学ぶこと |
|---|---|---|---|
| 操作試作 | ピザ2種 | 下処理台、オーブン | 組立、加熱、箱詰め、配達 |
| 本編序盤 | ピザ＋サラダ | 既存設備のみ | 加熱料理と非加熱料理の優先順位 |
| 本編中盤1 | バーガー | 鉄板を追加 | 別工程の並行処理と最終合流 |
| 本編中盤2 | スープ／カレー | 鍋を追加 | バッチ調理と取り分け |
| 以降 | 各系統の派生 | 原則として既存設備 | 食材と注文構成で変化を作る |

ピザ2種だけで製品MVPを完成させる必要はない。最初の操作・通信・配達試作にはピザを使い、その基礎が動いた時点でサラダかバーガーを一つ入れ、「別の工程系統を追加しても破綻しないか」までMVPで確認する案がよい。

## 7. 出張営業との組み合わせ

| 出張営業 | 推奨料理 | 理由 |
|---|---|---|
| 工事中の屋上レストラン | ピザ | 完成品をまとめてリフト輸送しやすい |
| 川下りレストラン | バーガー | 二隻で部品を作り、接岸時に合流できる |
| 祭り会場の臨時屋台 | サラダ／サンドイッチ | 群衆ギミックへ注意を割ける |
| 港の補給キッチン | スープ／カレー | 補給便とバッチ調理の計画が噛み合う |
| 空飛ぶレストラン | 既知のピザかバーガー | 強い環境変化と新レシピを重ねない |

料理系統と厨房ギミックを意図的に組み合わせる。ただし、初登場の料理と初登場の強いギミックは同じ営業に置かない。

## 8. 現時点で変更しないもの

業態が変わっても、次は維持する。

- 料理から配達までを一続きにする
- 本店は安定した成長拠点にする
- 出張営業では同じ操作と料理状態を使う
- ソロとマルチを別ジャンルにしない
- 経営は次の営業の設備、動線、役割を変える範囲に留める
- 一件の注文失敗で営業を終了させない

## 9. 決定が必要な点

1. ゲーム内で店を何と呼ぶか
2. MVPの意味を、技術試作までとするか、プレイヤーへ見せる最小製品版までとするか
3. ピザ以外で最初に追加する工程系統を、サラダ、バーガー、スープのどれにするか
4. 本店の見た目を、客席のある食堂中心にするか、厨房と配送ガレージ中心にするか
