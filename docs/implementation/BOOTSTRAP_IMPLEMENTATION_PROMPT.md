## 技術方針

- 正式採用エンジンは Unity 6.3 LTS。
- 3DレンダリングはURP。
- 対象はiPhone、横持ち、Metal。
- コードはC#。
- Unity Input Systemを使い、タッチ操作とEditor用キーボード操作を同じ入力コマンドへ変換する。
- Unity Test FrameworkでEditModeテストとPlayModeテストを用意する。
- 本番用3Dアセットはまだ作らず、プリミティブ、単色マテリアル、簡単なアイコンによるグレーボックスを使う。
- 広告、課金、本番サーバー、ランキング、本番マルチプレイは今回まだ組み込まない。交換可能な境界だけ用意する。
- Unity以外へ変更する必要がある場合は、実装前に理由、代替案、移行影響をADRへ記録し、ユーザーへ確認する。現在の正式採用を実装担当の判断だけで変更しない。

最初にローカル環境のUnity Hub、Unity Editor、Xcode、Gitの状態を読み取りで確認してください。必要なアプリやモジュールがない場合は、勝手な大規模ダウンロードを行わず、不足物と導入手順を報告してください。

## アーキテクチャ

少なくとも次の境界を作ってください。名前は既存プロジェクトの事情に合わせて微調整できます。

- `CookedOut.Domain`: Unity APIへ依存しない純粋C#のゲームルール
- `CookedOut.Application`: 営業開始、注文進行、スコア確定等のユースケース
- `CookedOut.Presentation`: MonoBehaviour、カメラ、HUD、入力、演出
- `CookedOut.Infrastructure`: セーブ、時刻、乱数、分析、将来のネットワーク接続口
- `CookedOut.Tests`: DomainとUnity統合テスト

料理、食材、工程、注文、ステージ、星ラインは安定した文字列IDを持つデータとして定義してください。表示名やPrefab参照をゲームルールへ直書きしないでください。

厨房の床、穴、壁、設備、提供口、食材箱、スポーン地点、ギミック接続点は正方形の論理グリッドで定義してください。1セルは標準カウンター1台分とし、設備はセルへスナップします。キャラクター移動はマス移動にせず、グリッド上の連続移動を維持します。詳細は`docs/game-design/05_square_grid_kitchen_system.md`を参照してください。

本店は通常営業解放時から12×9全域固定です。店ランクによる床面積、閉鎖区画、設備ソケット拡張、厨房拡張商品を実装しないでください。既存の10×8等のチュートリアル厨房は出張営業なので、この決定を理由に変更しません。

時間依存処理は差し替え可能なClock、ランダム要素はSeed付きRandomSourceを介し、テストを再現可能にしてください。スコア計算、注文タイマー、食材状態遷移はMonoBehaviourへ直接埋め込まないでください。

将来のオンライン同期を考慮し、営業状態は可能な限りシリアライズ可能にします。ただし、初回縦切りでネットコードやサーバー権威方式を完成させようとしないでください。

## 今回の実装範囲

### フェーズ0: リポジトリとUnity基盤

1. リポジトリ状況を確認し、Git未初期化ならローカルGitを初期化する。リモート作成やpushはしない。
2. Unity 6.3 LTSの3D URPプロジェクトをこのディレクトリに作る。Unity生成物を適切に`.gitignore`へ追加する。
3. `Assets/_CookedOut`以下へ、Scripts、Tests、Scenes、Prefabs、Data、Art、Audioの基本構造を作る。
4. asmdefでDomain、Application、Presentation、Infrastructure、Testsを分離する。
5. `docs/implementation/ADR-001_ENGINE_AND_ARCHITECTURE.md` と `IMPLEMENTATION_STATUS.md` を作る。
6. バッチモードでテストを実行できるスクリプトまたは明確なコマンドを用意する。

### フェーズ1: 最小プレイ可能厨房

ソロ出張営業チュートリアル `1-1` のグレーボックスを作ります。

- 厨房全体が見える固定三人称カメラ
- 一人のプレイヤーキャラクター
- 移動、向いている近距離対象の自動選択、輪郭表示
- 持つ、置く、切る、ダッシュ
- 生レタス、切ったレタス、共通配達容器
- 食材箱、まな板、カウンター、容器置き場、提供口、ゴミ箱
- 一種類の注文「レタスサラダ」
- 取る → 置く → 切る → 容器へ組む → 提供する、という完全な一注文
- 注文タイマー、営業タイマー、基本点、残り時間チップ、注文失効
- 結果画面と星0〜3
- 誤った状態では提供できず、理由をデバッグ表示できる
- キーボード操作と画面上の仮タッチUI
- 仮アセットでも食材状態を色だけに依存せず、形またはアイコンで区別する

この段階では食材投げ、加熱、火災、皿洗い、バイク配達、配送代行、動的厨房、マルチプレイを実装しません。後のフェーズへ安全に追加できるデータと状態遷移だけ用意してください。

### フェーズ2以降の計画だけ作る

実装せず、`IMPLEMENTATION_STATUS.md`へ依存順を記載してください。

1. 食材・完成配達容器の投げ
2. 野菜スープ、鍋、焦げ、火災、消火器
3. 外部配達型、バイク、自前配達、配達代行
4. 本店通常営業、コイン、設備レベル1〜5
5. 出張営業ギミック
6. 2〜4人オンライン協力
7. 認証、クラウドセーブ、報酬検証、分析
8. 広告、広告削除課金、外見課金

## 必須テスト

最低限、次を自動テストしてください。

- 生レタスを切ると切済み状態になる
- 未切断レタスでは料理が完成しない
- 必要部品が揃うと配達容器上でサラダが完成する
- 完成前の注文を提供できない
- 完成注文の提供で基本点と時間チップが加算される
- 注文失効で得点されない
- 営業終了時に正しい星が決まる
- 同じSeedと操作列で同じ注文結果になる
- Unity Scene上で一注文を最後まで完了できるPlayModeテスト、または同等の統合テスト

## 完了条件

- Unity Editorで `1-1` を開始し、一注文を完成・提供して結果画面まで到達できる。
- Consoleに未処理例外とエラーがない。
- 自動テストがすべて成功する。
- iOS向けビルド設定が横持ちになっている。
- 可能なら開発用iOSビルドを作る。署名や端末設定で不可能なら、UnityからXcodeプロジェクト生成まで検証する。
- 実装済み、未実装、仮定、既知の問題、テスト結果を `IMPLEMENTATION_STATUS.md` に記録する。
- 最後に変更ファイル、実行方法、テスト結果、次の一手を簡潔に報告する。

進行中は長時間無言にせず、節目ごとに短い状況更新をしてください。既存文書と無関係なファイルを削除せず、ユーザーの変更を保持してください。
